# 同类开源项目调研与对照

> 2026-09-05。对"美股披露数据聚合"这一类开源项目做的多源调研，25 条断言经 3 票对抗式验证，
> **18 条确认、7 条被推翻**。本文只记录经过验证的结论，并逐条对照 stock-radar 当前实现。
>
> 每条都标了投票结果。`3-0` = 三名独立验证者一致确认；`2-1` = 有一票异议；被推翻的断言单列在最后，
> **不要引用**——它们看起来很像"常识"，正是容易被误用的部分。

## 摘要

- **国会交易这一层没有可靠的现成数据源**。社区广泛引用的两个数据集都已冻结数年，
  唯一活跃的项目由商业厂商供数且自曝三大缺口。自建对官方源的抓取是唯一可靠路径。
- **两条官方链路都有成熟参考实现可抄**：参议院 eFD 的握手模式被 60+ 仓库复刻；
  众议院 PTR 的 PDF 表格抽取有公开实现。
- **扫描件 OCR 是整个社区的普遍未解问题**，所有实现都是"跳过"而非"解析"。覆盖缺口应显式记录。
- **SEC 侧相反**：`edgartools` 一个库覆盖了身份声明、限流、缓存、Form 3/4/5 与 13F 解析，
  是投入产出比最高的借鉴对象——但它救不了共享 IP 被限流的问题。
- **合规最硬的红线是商业 API**：Quiver 的 ToS 禁止任何形式的再分发（含非商业）。

## 一、国会交易追踪类项目

### 1.1 不要把现成数据集当生产数据源 `3-0`

| 项目 | 实际状态 |

| [`timothycarambat/senate-stock-watcher-data`](https://github.com/timothycarambat/senate-stock-watcher-data) | README 写「will be updated continually」，但 master 最新提交是 **2021-03-16**，全史仅 12 次提交，无 release 资产。截至 2026-09 已陈旧约 5.5 年 |
| [`neelsomani/senator-filings`](https://github.com/neelsomani/senator-filings) | 412 stars / 44 forks，但最后一次**人类实质代码提交是 2020-05-27**，其后全是 dependabot 的 lxml 升级（末次 2022-01-18） |

> **对 stock-radar**：结论成立且已执行——默认 provider 是 `house_clerk` + `senate_efd`，
> 旧镜像降级为 `stockwatcher` provider，仅在填了 `*_mirror_url`（自建镜像）时才有用。

### 1.2 参议院 eFD 握手：社区标准解法 `3-0`

```
requests.Session()
  GET  /search/home/                 → 从隐藏字段取 csrfmiddlewaretoken
  POST /search/home/                 → {csrfmiddlewaretoken, prohibition_agreement: '1'}，带 Referer
       从 cookie 取 csrftoken（需兼容旧名 'csrf'）
  POST /search/report/data/          → 同一 Session，返回 DataTables JSON
```

GitHub 代码搜索 `prohibition_agreement csrfmiddlewaretoken language:python` 返回
**67 个独立仓库**，2026 年的仓库仍在用同一流程，说明模式未过时。
`dannguyen/scrape-senate-financial-disclosures` 额外把 `X-CSRFToken` 放进请求头，是更稳的变体。

> **对 stock-radar**：`stock_radar/senate_efd.py` 的实现与此完全一致，
> 且已经在用 `X-CSRFToken` 请求头这个更稳的变体。
> **已改进**：cookie 名增加了 `csrf` 旧名回退。

### 1.3 备选形态：无头浏览器绕开握手 `3-0`

[`jeremiak/us-senate-financial-disclosure-scraper`](https://github.com/jeremiak/us-senate-financial-disclosure-scraper)
用 Puppeteer 点击 `#agree_statement` → `#filerTypeLabelSenator` → 提交，cookie 由 Chromium 隐式携带；
翻页循环点 `.paginate_button.next` 直到带 `disabled` 类。验证者 clone 后 grep 确认**全仓零 csrf/cookie/token 处理**，
即确实是"绕开"而非"实现"。

**时效警告**：该仓库用的是 Puppeteer 2.x 和已在 v14+ 移除的 `page.waitFor()`，**不能开箱运行**，只能当设计参考。

> **对 stock-radar**：纯 requests 方案更适合单人自用工具（轻、快、无浏览器依赖）。
> 浏览器方案留作 eFD DOM 变更后的应急后备。

### 1.4 众议院 PTR PDF 抽取：pdfplumber `3-0`

[`burd5/congress_stock_trading`](https://github.com/burd5/congress_stock_trading) 的路径：
Selenium 翻 DataTables → 过滤第 4 列 `== 'PTR Original'` 取 PDF href →
`pdfplumber.open()` 以 `{vertical_strategy:'lines', horizontal_strategy:'lines',
explicit_vertical_lines: 由 page.debug_tablefinder() 推导}` 抽表 →
按交易代码 `['P','S','SP','E','S (partial)']` 过滤。

**两点必须知道的修正**：

1. README 宣称用 BeautifulSoup，但两个 scraper 里 `soup = BeautifulSoup('html','lxml')` 是**死代码**，
   真正干活的是 Selenium + pdfplumber。
2. README 里的 "Camelot/Tabula 对比"只是 `tried`，**没有任何公开精度指标**——
   不能引用本仓库作为抽取准确率的证据。

该仓库大量使用硬编码绝对 XPath 与 `time.sleep()`，末次提交距今约 13 个月，属设计参考而非可运行方案。

> **对 stock-radar**：我们用 pypdf 文本抽取 + 行结构解析，已在真实申报上线上验证通过。
> pdfplumber 的表格线策略理论上更结构化，但**证据强度不足以支撑重写**（对方无精度数据）。
> 保持现状，列为可选优化。

### 1.5 扫描件是全社区的未解问题 —— 必须显式承认 `3-0 ×3`

- `neelsomani/senator-filings`：按链接前缀 `/search/view/paper/` 判定纸质件，直接 return 空 DataFrame，
  代码注释就是 `We cannot parse PDFs`，全仓无任何 PDF/OCR 依赖。
- `burd5`：line-strategy pdfplumber 遇到无文本层的扫描件抽出空表，被 **bare except 吞掉，静默丢件**。
- `kadoa-org/congress-trading-monitor`：把 `Senate pre-2015 paper-filing PDFs (currently skipped)` 列为未来计划。

旁证：确有专门项目在评估参议院扫描件 OCR 精度（`dannguyen/abbyy-finereader-ocr-senate`），
说明这是被公认为难题的独立课题。

> **对 stock-radar — 已改进**：原本给 PDF 链接但不报数量，一个薄的板块会看起来像"这周没人交易"。
> 现在两院都会在数据源状态里写明「N/M 份是扫描件，抽不出交易明细」。

### 1.6 ticker 解析的真实上限：约 68% `3-0`

验证者下载 `congress-trading-monitor` 公开的 `trades.json`（5000 条，至 2026-09-03）实际统计：
**1609 条（32.2%）ticker 为 null**（oge_executive 1057、house_clerk 444、senate_efd 108），
且有明确误漏（`SDZNY- Sandoz Group AG ADR` ticker=null、26 条 `type='Stock'` 却无 ticker、
asset_name 里残留 HTML 空白垃圾）。这是**该项目自己发布的数据**，属最强证据类型。

> **对 stock-radar**：设计原则应是「可空 + 保留原始 asset_name + 解析失败不丢行」。
> 现有实现符合：`is_equity` 同时看 ticker 和资产类型代码（`[ST]` 等），
> 所以一个抽不出代码的股票行仍会保留。另外**不少空 ticker 是合法的非股票资产**
> （市政债、结构化票据、非上市公司），不是 bug。

## 二、SEC EDGAR 访问与限流

### 2.1 `edgartools` 是投入产出比最高的借鉴对象 `3-0`

[`dgunning/edgartools`](https://github.com/dgunning/edgartools) 一个库同时解决：

| 能力 | 实现 |
| --- | --- |
| 身份声明 | `set_identity()` / `EDGAR_IDENTITY` 环境变量 → 写进 `headers['User-Agent']`；取不到直接 `raise IdentityNotSetError()` |
| 限流 | import 期构建单例，默认 **9 req/s**（低于 SEC 的 10）的 pyrate_limiter 令牌桶 |
| 缓存 | 默认开启 Hishel 磁盘 HTTP 缓存 |
| 退避 | 429 的 `Retry-After` 解析 + 指数退避（quick 5 次/16s，bulk 8 次/120s） |

无需 API key、无需注册、无限流分级。接受的 UA 格式：`Name email@domain.com`（推荐）、纯 email、
或 `Company Name contact@company.com`。

### 2.2 但它救不了共享 IP —— 这是两个不同的轴 `3-0`

**这是本次调研对 stock-radar 最关键的一条**：

> 声明 UA 只解决 **"Your Request Originates from an Undeclared Automated Tool"** 这一种 403。
> 对 **"Request Rate Threshold Exceeded"** 以及云主机 / GitHub Actions 共享出口 IP 的信誉封锁**无效**。

机理也被验证者从源码确认：edgartools 的限流用的是 `InMemoryBucket`，**per-process 生效**，
多进程 / 多 async worker / 多个共享出口 IP 的 runner 之间**不协调**——
这正是共享 IP 被限流的原因，换库不解决。

另注意：`httprequests.py:65-66` 的 `max_requests_per_second=8` 是死代码，真实默认是 `httpclient.py` 里的 9。

> **对 stock-radar**：昨晚"SEC 板块只能在本机跑"的结论**得到独立印证**。
> 我们探针实测抓到的两种 403 页面（`Request Rate Threshold Exceeded` /
> `Undeclared Automated Tool`）正好对应这两个轴，报告里已经分别给出对应的处理建议。

### 2.3 是否要切到 edgartools？

**未决**。取舍：

| 切过去 | 保持现状 |
| --- | --- |
| ✅ 已修的坑（见下节四个 issue） | ✅ 依赖只有 3 个，无人值守时故障面小 |
| ✅ 限流/缓存/退避不用自己写 | ✅ 现有代码已有离线测试覆盖 |
| ❌ 重依赖，故障面变大 | ❌ 13F/Form 4 的边角情况要自己踩 |
| ❌ 不解决最大的问题（共享 IP） | |

## 三、Form 4 / 13F 解析的坑

### 3.1 13F 的四个经典坑，edgartools 都处理了 `3-0`

| 坑 | edgartools 的处理 | 对应 issue |
| --- | --- | --- |
| 千美元 / 美元单位切换（Q4 2022 前后） | `if in_thousands: df['Value'] *= 1000` 显式换算 | `#749` |
| PutCall 衍生品行 | 专门处理 | `#824` |
| 13F-HR/A 的 RESTATEMENT vs NEW HOLDINGS 语义 | 专门处理 | `#872` |
| 2013 年前定宽 TXT 的 CUSIP 串列丢行 | 三种历史编码 xml/txt/html 均有解析器 | `#1072` |

季度对比由 `HoldingsComparison` 用 `np.select` 产出 `['NEW','CLOSED','INCREASED','DECREASED']`。

**这四个 issue 编号就是一份现成的测试用例清单**——全部已关闭，既证明坑真实存在，也证明有参考解法。

> **对 stock-radar**：
> - 单位换算 ✅ 已处理（我们按"每股隐含价格中位数"推断，不硬编码年份，比按日期切更稳）
> - PutCall ✅ 已处理（`Holding.slot` 包含 `put_call`，所以同一 CUSIP 的正股和期权不会互相抵消）
> - 修正案语义 ⚠️ 未处理
> - 老式 TXT ❌ 不支持（`primary_xml()` 只找 `.xml`）——对日更工具影响很小

另注意：`holdings` 按 CUSIP 聚合、`infotable` 保留 per-manager 明细，需按用途刻意选择；
`Ticker` 列是 best-effort 的 CUSIP→ticker 解析，**不具权威性**。

### 3.2 Form 4 聚合的四个陷阱 `3-0`

edgartools 官方指南的 Common Pitfalls：

1. **单份 Form 4 可含多笔交易**（Table I 非衍生 / Table II 衍生天然多行）
2. **`4/A` 是对既有申报的修正，朴素聚合会重复计数** —— 该库对修正案是"透明解析"，去重责任在聚合方
3. **可能是经信托或其他实体的间接持有**（`ownership == 'I'`，Rule 16a-8）
4. **部分交易是期权/权证等衍生品而非普通股**

> **对 stock-radar**：
> - 陷阱 1 ✅ 一直支持（每笔交易一个 Item）
> - 陷阱 4 ✅ 一直支持（`derivative` 标记 + 标题里的"(衍生品)"）
> - 陷阱 2 ❌ **原本是 bug** —— 我们把 `4` 和 `4/A` 一视同仁，同一笔会算两次。
>   **已修**：解析 `dateOfOriginalSubmission` 标记修正申报，标题加【修正申报】，
>   摘要写明"不是新增交易，统计时勿与原件重复计数"。
> - 陷阱 3 ❌ 原本没有。**已修**：解析 `ownershipNature/directOrIndirectOwnership`，
>   标 `[间接持有]` 并附持有形式（如 "By Family Trust"）。

### 3.3 健壮性告警

来自已关闭 issue（历史限定，非现存反驳）：`#887` 非衍生交易缺 `transactionCoding` 时会抛
`AttributeError`、`#865` 逐笔脚注归属为空。

> **对 stock-radar**：我们的 `parse_form4` 已用 `text_of()` 做空值安全的嵌套查找，
> 缺字段返回 `''` 而不抛异常；`ParseError` 也被捕获并记为警告。

## 四、简报层：可直接借鉴的两个设计

### 4.1 rss2email：最轻量的跨天去重 `3-0`

单个 JSON 文件做 feed 数据库（`$XDG_DATA_HOME/rss2email.json`），
持久化每个 feed 的已见条目 GUID 集合；`_process_entry()` 以 guid 查 `self.seen`，
命中则 `return None`。写入用 tmp 文件 + `os.replace` 原子替换。

**必须一并抄走的教训**：

1. **并发能力近乎没有** —— 只有 UNIX 下的 `fcntl` 共享锁（`LOCK_SH`），读-改-写外面没有 `LOCK_EX`，
   非 UNIX 直接跳过。两个并发 run 会丢更新，**调度上必须保证单实例**。
2. **去重键要一次定死** —— rss2email 的 UID 取决于 `trust-link`/`trust-guid` 配置，
   事后切换会导致老条目按新键**重新推送**。
3. **首次运行会推送全部历史 backlog**，除非显式抑制。

> **对 stock-radar**：我们用 SQLite 而非 JSON，锁的问题天然更好；
> 键已经为每类记录定死（PTR 用 `doc_id + 行序号`、Form 4 用 `accession + 交易序号 + 代码 + 股数 + 价格`），
> 且写进了文档。首次 backlog 的行为 README 已注明。

### 4.2 RSSbrew：digest 作为一等对象 `3-0`

`models.py` 里有真正的 `class Digest(models.Model)`，`ProcessedFeed` 上挂
`toggle_digest` / `digest_frequency`（daily 或 weekly）/ **`last_digest`（DateTimeField，跨运行水位线）** /
`use_ai_digest` / `additional_prompt_for_digest`。摘要分两层：逐条摘要 + 整篇 digest 摘要（opt-in，默认关）。

> **对 stock-radar 的直接映射**：`last_digest` 式**时间水位线比"按日期重算"更稳**，
> 且天然支持手动重跑；把频率、开关做成配置字段能让同一套管线同时产出"每日全量"和"每周精选"。
> **未实现，值得做。** 许可为 AGPL-3.0（借鉴设计无碍，复制代码有传染性）。

## 五、合规

### 5.1 商业 API 不能作为公开简报的数据源 `2-1 / 3-0`

Quiver Quantitative 的 ToS（更新至 2026-06-25）构成两道禁令：

1. 不得 redistribute / republish / resell / sublicense / broadcast 或以任何方式向第三方提供 Quiver Data，
   **"whether for commercial purposes or otherwise"**（明确含非商业）。数据授权为 personal, non-commercial use only。
2. 禁止用 robot / spider / 任何自动化手段访问其网站与 App，"for any purpose, including monitoring or copying"。

**三点措辞修正**（验证者要求向下传递）：

- 违反 ToS 是**违约**（可能叠加 CFAA / hot-news 风险），**不等于"违法"**。
- "仅严格单用户私用可辩护"是风险判断，**不是 ToS 原文**。
- 该限制**只约束「从 Quiver 取得的数据」**。同样的事实若直接取自
  disclosures-clerk.house.gov / efdsearch.senate.gov / SEC EDGAR 则不受此合同约束，
  且事实本身在 *Feist* 之下不受版权保护。

旁证：Quiver 无免费 API 档位（Hobbyist $30/mo、Trader $75/mo、Commercial 询价），
免费只有网页浏览——这正解释了抓取动机。

> **对 stock-radar**：`quiver` provider 走的是付费 API（合规），但开了就只能自己看。
> README 的「合规注意」章节已写明。**抓它的网页当免费替代属于违约，不要做。**

## 六、整体架构建议 `medium · 综合推论，未独立投票`

**最优形态**：本机/单实例 cron + 直连政府一手源 + SEC 全链路交给成熟库 +
轻量已见集合 + `last_digest` 水位线 + 模板渲染多格式输出。

**应避免的失败模式**（每条的事实基础都是 3-0 通过的）：

| 失败模式 | 证据来源 |
| --- | --- |
| 依赖第三方镜像数据集（会静默冻结数年） | §1.1 |
| 硬编码绝对 XPath + `time.sleep()` 的浏览器脚本（易碎且已不可运行） | §1.3 §1.4 |
| 扫描件解析失败被 bare except 静默吞掉且不计数 | §1.5 |
| 假设 ticker 解析 100% 成功而丢弃无法映射的行 | §1.6 |
| 在多 runner / 共享出口 IP 上并发打 EDGAR | §2.2 |
| 把商业 API 数据放进任何公开渠道 | §5.1 |

> **覆盖度声明**：本轮**未获得** GitHub Actions vs 本机运行的一手量化证据，
> 也**未覆盖** Huginn / n8n / changedetection.io / newsboat 生态的具体设计。
> 形态对比这一角度的覆盖度弱于其他四个角度，标为 medium。
